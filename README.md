# O O M A - Offline Order management App

O O M A is a local-first order and payment manager for Android, iOS, and the web. Users can create an account on the device, manage saved card names and mobile numbers, record customer orders, and track automatic and manual payment records.

The current project is an **Expo React Native application**, not a traditional MERN application. It does not currently contain an Express server, MongoDB database, or separate Node.js API. Application data is stored locally with SQLite on each device.

## Features

- Local account registration and login
- Multiple accounts stored on the same device
- Optional session restoration for 12 hours or 1 day
- Home dashboard with order and payment totals
- Order creation, editing, deletion, and automatic payment creation
- Manual payment creation, editing, and deletion
- Saved card names and mobile numbers for use in orders and payments
- Per-user data isolation in the local database
- Android, iOS, and Expo web development targets

## Tech Stack

- **Framework:** Expo SDK 54
- **UI:** React 19.1, React Native 0.81
- **Language:** TypeScript 5.9 with strict mode enabled
- **Navigation:** Expo Router 6 and React Navigation bottom tabs
- **Persistence:** `expo-sqlite` with SQLite database `offline_order_manager_v2.db`
- **Icons and device features:** Expo vector icons, haptics, status bar, splash screen, and system UI packages
- **Tooling:** npm, ESLint 9, `eslint-config-expo`

## Prerequisites

Install the following before starting development:

- Node.js LTS and npm
- Git
- For Android development: Android Studio, an Android SDK/emulator, and a configured `ANDROID_HOME`
- For iOS development: macOS with Xcode and an iOS simulator
- A physical device can use Expo Go for supported development features, or a local development build for native features

Expo SDK 54 documentation: [docs.expo.dev/versions/v54.0.0](https://docs.expo.dev/versions/v54.0.0/)

## Environment Variables

No environment variables are required by the current application. There is no `.env` file and no API endpoint or external database configuration in the source code.

The app is intentionally local-first. If a future backend is added, public Expo variables can use the `EXPO_PUBLIC_` prefix, for example:

```env
EXPO_PUBLIC_API_URL=http://localhost:3000
```

Do not place passwords, API secrets, private keys, or other credentials in `EXPO_PUBLIC_` variables because Expo exposes them to the client bundle.

## Install Dependencies

From the repository root:

npm install

## Run Locally

Start the Expo development server:

```bash
npm run start
```

Then choose a target from the Expo CLI, or use one of the direct commands below.

### Android

Start the app in an Android emulator or on a connected Android device:

```bash
npm run android
```

This uses the native Android project in `android/` and may require Android Studio, a running emulator, and the Android SDK to be configured.

### iOS

On macOS with Xcode installed:

```bash
npm run ios
```

The iOS command is not available on Windows because Apple tooling requires macOS.

### Web

Start the web target with:

```bash
npm run web
```

The primary persistence path is native SQLite. Verify web behavior for the specific browser and Expo SDK configuration before treating web as a production deployment target.

## Data Storage and Account Behavior

On first launch, the app initializes the SQLite schema and creates the local database file. The database includes users, user settings, the active session, saved device username, cards, mobile numbers, orders, and payments.

All records are scoped to the local user ID. Deleting a card or mobile number keeps historical order and payment rows, while their related display value becomes unavailable. Creating an order also creates its associated automatic payment in a transaction. Manual payments have no associated order and can be edited or deleted.

The current authentication implementation stores passwords directly in the local SQLite database. This is suitable only for a local prototype or trusted-device scenario. A production release should use a backend authentication service and password hashing, secure credential storage, encrypted data handling, and a defined backup or synchronization strategy.
